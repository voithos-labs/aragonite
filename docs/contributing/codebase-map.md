# The codebase map

So, I've noticed a slight blocker to people working on this repo - namely the few hundred source files in it. Skill issue honestly, but i'll play nice.

What's in this doc:

1. **The behavior → entry table**: the thing you saw break, the file that owns it, and the rule
   people keep breaking there.
2. **Keyboard and chords**: how a keypress becomes a command, and the one gate that inverts the
   codebase's usual instincts.
3. **The reveal path**: how you touch a block that windowing has unmounted.
4. **Blank lines and separators**: the family of helpers that keeps blank lines honest, and the
   join-cleanup family beside it.
5. **Keeping this map fresh**: the lint that checks every reference here, and how to add a row.

**Altitude.** Files and responsibilities only. No line numbers, no signatures, and no code beyond
a one-line call where its output is the quickest way to see a shape. A file is named by its full
path from the repo root; a symbol only where the symbol is the thing to find, written
`path :: Symbol`. Every such reference is machine-checked (§ Keeping this map fresh), so it
either resolves or the gate goes red.

**How to read a row.** The entry is where you put the breakpoint. The rule is the thing that's
been broken before, and nearly every one is the same rule in a different costume, rule 4 of
`docs/contributing/rules.md`: a behavior's logic lives at the one place every path crosses, not
at the call sites. So when you want to add a branch at one of these files, the rule in that row
is what you're arguing with.

A few of the words the repo coined survive in symbol names (`caret-doors.ts`, `HeightOracle`,
`clampToLandableRaw`). Since this may be your first doc in the repo, keep
[`glossary.md`](glossary.md) open beside it; every one of them is a line there.

## Keyboard and chords

The facts, and then the manifest.

**`Mod` folds Ctrl and Cmd, unconditionally.** `src/lib/schema/keybindings.ts` :: `eventToChord`
turns a `KeyboardEvent` into a normalized chord, and `e.ctrlKey || e.metaKey` becomes the single
token `Mod`:

```ts
eventToChord(new KeyboardEvent('keydown', { key: 'b', ctrlKey: true })); // 'Mod+B'
eventToChord(new KeyboardEvent('keydown', { key: 'b', metaKey: true })); // 'Mod+B', the same string
eventToChord(new KeyboardEvent('keydown', { key: 'z', ctrlKey: true, shiftKey: true })); // 'Mod+Shift+Z'
eventToChord(new KeyboardEvent('keydown', { key: 'Shift', shiftKey: true })); // null: a held modifier isn't a chord yet
```

There's deliberately no platform detection anywhere in the tree (no `navigator.platform` read,
no `isMac`). A Mac user's Cmd and a Windows user's Ctrl produce the identical chord string, so
nothing downstream needs to know which one was pressed. The Playwright harness does have to press
a real OS key, so its helpers spell every editor chord `ControlOrMeta` and let Playwright resolve
it (a few specs still press a literal `Control+z` or `Control+a`, which only works off a Mac). A
chord the editor doesn't claim (native word-jump, word-delete) stays literal `Control`, because
macOS binds those gestures to a different key. The fold still needs a unit guard: a branch that
reads `ctrlKey` alone and drops Cmd is invisible to e2e (on a Linux runner, Meta _is_ the wrong
key), so its regression test belongs in the unit suite, driven through a synthetic event like the
ones above.

**Where a chord resolves, and where a new branch goes.** A chord resolves through
`src/lib/schema/commands.ts` :: `resolveBinding`, in the order `docs/design/editor.md` § 5 lays
out (the consumer's overrides, then the kind's own `keymap`, the editor-global keymap, and the
plugin-global tier last). It takes the chord, the kind, the consumer's overrides and which
plugins are on, and hands back the binding, or `null` when nobody claims the chord:

```ts
const all = everyInstalledPlugin; // src/lib/schema/plugin-activation.ts
resolveBinding('Mod+B', 'paragraph', undefined, all); // { chord: 'Mod+B', command: 'format.toggleStrong' } the kind's own keymap
resolveBinding('Mod+Z', 'fencedCode', undefined, all); // { chord: 'Mod+Z', command: 'history.undo' } the editor-global keymap
resolveBinding('Mod+Q', 'paragraph', undefined, all); // null
```

Container bubble resolution (`resolveKindBinding`) deliberately stops before the global tier, so
a container never re-fires undo for the leaf inside it.

A keystroke belongs in a keymap when it maps to a **command**: a named id the focused block's
`runCommand` or a global handler can run. Bare keys are welcome there (Enter, Tab, Backspace and
Delete are all ordinary keymap entries on prose kinds). A keystroke stays a hand-written keydown
branch only when the command channel genuinely can't carry it: the gesture needs an event a
keydown doesn't have (whole-block copy needs a `ClipboardEvent`), or it belongs to a transient
state rather than a kind (a selected inline widget, an open menu's focus trap, the gap caret's
proxy). If you find yourself writing the second kind, you're adding a site that claims a chord by
hand, and it has to join the manifest.

**The G4.29 authoring constraint**, verbatim from the header of
`src/lib/schema/reserved-chords.ts`:

> A listed file keeps its literal key comparisons and modifier reads, the scan's evidence.

This is the one place the codebase's own instinct (share the logic, put it where every path
crosses) is inverted, and it surprises everyone. Extracting four `e.key === 'ArrowUp'` branches
behind a shared `isVerticalArrow()` helper is exactly what rule 4 asks for, and it will fail
`src/lib/test/invariants/lint/reserved-chord-manifest.test.ts`. The manifest is written by hand,
and that test scans every library file that reads a modifier flag and checks each entry's listed
keys against the literals in its file; take the literals away and the evidence is gone. The gate
buys something the extraction would cost: `reservedChords()`, the public answer a host page reads
to avoid colliding with the editor (a `Set` of chord strings like `'Mod+B'`), stays honest by
construction. If you need the helper anyway, teach the scan about it first.

**The manifest itself** is `src/lib/schema/reserved-chords.ts` :: `HARDCODED_CHORD_SITES`: one
entry per library file that reads a modifier flag, listing the chords it claims outside every
keymap and the key literals it compares. Read it there; a copy here would rot, and the gate only
guards the original.

## The reveal path

The question this answers: a document is windowed, the block you must touch isn't mounted, and
you need its DOM. Undo restore, a search jump, a consumer's `setSelection`, and a cross-block
collapse all hit this. It gets its own section because the chain runs through most of the
rendering stack and no single file along it names the whole path.

```mermaid
flowchart TD
    CALLER["a caller that must touch DOM"] --> PICK{"which primitive?"}
    PICK -->|"mount only (a history swap)"| MOUNT["reveal the path"]
    PICK -->|"mount + viewport (a navigation)"| SCROLL["hold the target, mount, scroll"]
    SCROLL --> MOUNT
    MOUNT --> LEVEL["descend one path level"]
    LEVEL --> HIDDEN{"into a collapsed body?"}
    HIDDEN -->|"yes, and it may open one"| OPEN["open it: one undo entry"]
    HIDDEN -->|"yes, and it may not"| GIVEUP
    OPEN --> SLOT
    HIDDEN -->|no| SLOT{"child's component ref set?"}
    SLOT -->|yes| NEXT["next level"]
    SLOT -->|no| WRITE["the list asks the scroll owner<br/>to scroll to the index's offset"]
    WRITE --> INWIN{"index still in window?"}
    INWIN -->|"provably not"| GIVEUP["give up now; the caller<br/>degrades to path state (VR-5)"]
    INWIN -->|yes| PUB["the list re-slices, the host<br/>mounts and hands up its ref"]
    PUB -->|"one tick later"| NEXT
    NEXT --> LEVEL
    LEVEL -->|"path exhausted"| CARET["place the real caret"]
```

**Two primitives, and callers pick one on purpose.** The caret landing's `mount` is the **mount**
primitive: it makes the target exist and doesn't scroll the editor to it (a table it passes
through still scrolls its own grid sideways to a far cell's column, or the caret would land where
you can't see it). `src/lib/editor-rects.ts` :: `createEditorRects` wraps a mount as `scrollTo`,
which places, mounts, then scrolls once and keeps the block where it landed while the heights around it catch up (`place` on `src/lib/cursor/scroll-owner.ts` :: `createScrollOwner`, the one writer of
the scroll position). Only a navigation (the rects API: `reveal`, `scrollTo`, `navigateTo`, which
the outline and the search bar go through) opens a collapsed body on the way, as one undo entry,
since that's what gets it to a spot inside the hidden body.

A caret goes a third way, `src/lib/selection/caret-landing.ts` :: `createCaretLanding`:

- `land` takes an edit's caret (and the inline menu's, the link card's, a click below an
  unmounted tail);
- `navigate` takes `navigateTo`'s;
- `restore` takes a stored selection (undo and redo, a gap caret included, `setSelection`, a mode
  switch, a range collapsed by an arrow, the range a cross-block format toggle selects again, the
  find bar and link card handing the caret back);
- `park` takes the moving end of a Shift+Arrow range, which mustn't end the range.

They mount the same way, but a position inside a closed body lands on its title row instead of
opening it, unless it's a navigation's. A caret scrolls only when its line isn't fully visible,
the least distance that shows it (its whole block when that fits on screen) through the scroll
owner's `showRect`, letting go of the viewport as soon as it's done; only `navigate` holds its
block where it landed (no other caller can ask to), and a mode switch and the table menu's close
only mount. An arrow arrival asks the same way, through `followArrival`. The focus call that puts
the caret down never scrolls on its own.

**A caller asks for a reveal instead of reaching for an element.**
`src/lib/selection/caret-landing.ts` :: `createCaretLanding` decides which path actually needs to
be on screen (a table endpoint mounts its deep cell, a caret aimed at a list its first item), and
`src/lib/selection/selection-restore.ts` :: `restoreGapCaret`, which `restore` hands a recorded gap
caret to, mounts the block the gap sits against and brings it into view.

**Where a cell endpoint's caret goes is answered in one place.** An endpoint inside a table
addresses the table block by cell index, so every reveal and every caret placement asks
`src/lib/selection/selection-state.svelte.ts` :: `cellLandingFor` for the landing rather than
resolving the deep `[table, row, col]` path itself. A site that skips it places a cell index as a
character offset on the table wrapper, which lands somewhere in the grid's text.

**The scroll target is registered before the first await.** The scrolling wrapper calls the scroll
owner's `place` (`src/lib/cursor/scroll-owner.ts` :: `createScrollOwner`) _before_ its first
await, so the pointerdown that triggered the jump can't release its own pin (the hold that keeps
the revealed block in place while the page reflows around it), and the final scroll is skipped if
a newer reveal superseded it.

**The descent walks one child list per level.** `src/lib/reactivity/child-list.ts` ::
`descendTo` takes the root's `ChildList` and follows the path down; the root, every container, the
table and each table row provide one (their child refs, their render window, and whether they're
collapsed). At each level `src/lib/reactivity/publish-ref.svelte.ts` :: `revealChildOrWait`
short-circuits when the child's component ref is already set, and otherwise asks the list's
`revealChild` (`src/lib/reactivity/list-windowing.svelte.ts` :: `createListWindowing`) to scroll
straight to the height model's offset for that index, through the scroll owner's `scrollToMount`.
`src/lib/components/BlockList.svelte` re-slices and `src/lib/components/BlockHost.svelte` mounts
and hands up its ref.

**The window re-check is the termination guarantee, VR-5.** After that scroll the reveal reads
`isInWindow`. A recomputed window that excludes the index ends the reveal now, and inside the
window the mount is at most one tick away, so that tick is the whole wait. Every `ChildList` has
to answer `isInWindow`, so there's no list the descent could wait on forever.

**The caret goes down at the mount; the scroll comes after.** Once the target is mounted the
landing places the caret straight away (the block's `focus`, or
`src/lib/selection/native-bridge.ts` :: `applySelectionToDom` for a stored selection), and only
then brings it into view. An edit's or a restore's scroll is one write. A navigation's
(`navigate`, `rects.scrollTo`) keeps going after its first write: the scroll owner waits a tick
at a time while height corrections keep arriving, putting the block back from the height tables
each round, and stops once a flush passes with none. That's what survives images decoding above
the target.

Nested containers get their window from `src/lib/reactivity/use-container-windowing.svelte.ts`. A
table's rows window like any list; a row's cells never do, so the row's list scrolls a far column
into the grid's own box instead (`bringChildIntoView`, over the table's sideways scroll).

## Blank lines and separators

A blank line between two blocks isn't a node. It's the follower's `leadingTrivia`, which means a
blank paragraph **is** its follower's separating line, and any operation that fills, deletes, or
replaces a blank block has to restore a separator somebody else was relying on. Get it wrong and
the byte round-trip stays green while the document reparses to a different block count on
reload. That's the bug this family exists to prevent.

The settle helpers live together at the head of `src/lib/tree-operations/settle.ts`
(`clearRedundantSeparator`, `dropDoubledSeparator`, `restoreSeparatorOnFill`,
`restoreSeparatorAfterBlank`, `settleSeparatorOnBlank`). Two exist where one would seem to do
because their preconditions are facts about different nodes. Each takes the body, the children
plus the container that owns them (`src/lib/tree-operations/node-primitives.ts` :: `BodyParent`),
since that container's fence lines and title decide where a blank line may sit. Each writes
through one of the file's two writers: `writeSeparator` copies the child out of the undo snapshot
before it writes the child's blank line, and `writeWrapSlot` writes the blank line a fence strips
onto the owner itself. Almost nothing calls them by hand:
a splice settles through the two entries a splice can arrive by, `settleSeparator`, which the
commit steps run over every scope's change, and `spliceChildrenSettled`, which the
path-addressed helpers in `src/lib/tree-operations/path-mutate.ts` and
`src/lib/tree-operations/cleanup.ts` splice through. What stays hand-carried says why at the
site:

- `insertParagraph` in `src/lib/editor-actions/block-edit-core.ts`, the paragraph made between
  blocks by the gap caret, the trailing insert row, insert-below, and a character typed on a
  block focused whole (a thematic break, a plugin container); Enter on one goes to `splitBlock`
  instead;
- the content entry's own branches in `updateNodeContent`;
- a range delete inside one block, in `src/lib/selection/range-delete.ts`;
- the rotation in `src/lib/tree-operations/reorder.ts` :: `reorderChildrenWithTrivia`, which
  moves blank lines by position and asks `settleSeparatorOnBlank` for each one it moved.

One helper sits outside the family: `src/lib/tree-operations/list/sublist-separator.ts` ::
`settleSublistSeparator` gives a sublist whose first item is empty the line that keeps its marker
from reading as a setext underline. Three paths reach that shape and ask it: the nesting insert in
`src/lib/editor-actions/list-context.ts`, the chain rebuild in
`src/lib/tree-operations/chain-rebuild.ts` :: `rebuildUnsharedChain`, and the splice settle itself
(`src/lib/tree-operations/settle.ts` :: `settleEmptyMarkerLists`, which asks
`lacksSublistSeparator` and writes the line through its own writer). Read
`docs/design/syntax-tree.md` § Blank lines before touching any of it: two byte-equivalent trivia
shapes exist, and which one you're holding decides which helper applies.

The document's last line, the one line allowed no ending, has a file of its own beside them,
`src/lib/tree-operations/open-tail.ts`. The commit calls `endWindowLines` on every scope before
it repairs the blank lines around the edit (each placed block ends its line), and `keepOpenTail`
once the containers rebuild (a file that had no final break gets it taken off again). An edit
never writes that ending itself, except a move, which ends its own window before it checks its
joins until the commit settles them; a scan (G4.74) holds the walk to that file, and G1.41 checks
the result after every structural commit.

The settle helpers' sibling family is the **join absorb**, for the joins a reload reads as fewer
blocks, or as no fewer with the upper block holding content from the lower (a list newly standing
above indented code, a paragraph taking indented code whose whitespace lines come back as blank
blocks, a demoted heading no longer interrupting the paragraph under it, a paragraph put
directly above its own `===` underline); the tree converges to the reload's reading of such a
join, and `docs/design/editor.md` § 8 says why. `src/lib/tree-operations/settle.ts` ::
`absorbSeamReading` answers one join, and everything that disturbs one has to ask it the
question: `splitNode` asks it directly, while `deleteNode`, every settling return of
`updateNodeContent`, the one splice call behind `settleSeparator` and `spliceChildrenSettled`,
`src/lib/tree-operations/reorder.ts` :: `reorderChildrenWithTrivia`, and the container-slot ask
below all go through `absorbWindowSeams`, the window walker over both edges a splice disturbed.
Absorbing the join above leaves the predecessor holding the written bytes, so the content entry
reports where its text ended up, and `settledCaretPosition` is what each caret placement spends:
the keystroke at every depth, the cross-block typed character, the cross-block inline paste, and
the residue a matching list paste leaves.

One reading the absorb must never converge to is a construct the write itself left open, so the
content entry closes it before the ask, via `src/lib/tree-operations/content-write.ts` ::
`closeWrittenConstruct` (`docs/design/editor.md` § 6 has the rule and its one exception). The
class is the grammar's (bytes that swallow a blank line and a prose line absorb to EOF), not a
kind list.

One join no scope-local ask reaches is the one at a container's own slot, since a mutation inside
a container changes what the container interrupts, and that join lives in the grandparent's
array. `src/lib/tree-operations/chain-rebuild.ts` :: `rebuildUnsharedChain` asks it on the way out
of the ancestry rebuild, gated on a boundary line of the rebuilt raw moving; the collapse splices
a scope no commit descriptor covers, so `src/lib/editor-actions/ancestry-folds.ts` publishes that
scope's ids and refs and says where the caret goes for the child position it removed. The callback that does it is
required but nullable: a caller that can't reconcile a parent-scope splice passes `null` and
declines the ask. A declining caller whose chain is built from a leaf path below its commit scope
declines for that reason alone (the chain's collapse slots outrun the scope's descriptor), not
because a wider commit re-walks it. Which caller takes which stance, and why, is enumerated in
`src/lib/test/invariants/lint/ancestry-fold-sink-thread.test.ts` (G4.46).

## Keeping this map fresh

Two things hold it, and one of them isn't automatic.

`scripts/check-codebase-map.mjs` runs inside `npm run lint`, and on its own as
`npm run docs:map:check`. It reads every backticked `src/`, `docs/`, or `scripts/` span in this
file and in every other `docs/design` and `docs/contributing` doc, asserts the path exists, and
for a `path :: Symbol` span, that the symbol appears word-bounded in that file. A span that
doesn't start with one of those three roots isn't checked at all, so write the full path. It reads
the other direction too, over the whole tree: a `<doc>.md § Section name` pointer in any source
file or doc has to slug-match a heading that doc still carries. When everything resolves it prints
one line, counts and all, and exits 0:

```
$ npm run docs:map:check
codebase-map: … references resolve (… naming a symbol) across … files in docs/design, docs/contributing; … § pointers resolve across … files
```

When something doesn't, it prints each offending doc and span (a missing file, a symbol not found
in it, a malformed reference, a `§` pointer to a doc or heading that doesn't exist) and exits 1,
so `npm run lint` goes red with it. A `<name>` placeholder or a `*` glob names a family, so only
its concrete prefix resolves. So a deleted file or a renamed export goes red on the commit that
moves it. What the check does **not** do is notice that a responsibility moved while both names
survived, or that a rule stopped being true. That part is the habit: **a moved entry point moves
this map in the same commit**, and the lint is the thing that reminds you when you forget.

Adding a row is the same job in miniature: name the behavior the way a user would say it, the
file (or `path :: Symbol`) where its logic lives, the rule that's been broken there, and the spec
section that explains why. The lint checks your spans on the next `npm run lint`.

When the map runs out, go to `docs/README.md` and pick the design doc for the subsystem. This
file tells you which file to open; those tell you why it's shaped the way it is.
