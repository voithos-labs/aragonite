# The codebase map

So, I've noticed a slight blocker to people working on this repo - namely the few hundred source files in it. Skill issue honestly, but i'll play nice.

What's in this doc:

1. **The behavior → entry table**: the thing you saw break, the file that owns it, and the rule
   people keep breaking there.
2. **Keyboard and chords**: how a keypress becomes a command, and the one lint that inverts the
   codebase's usual instincts.
3. **The reveal path**: how you touch a block that windowing has unmounted.
4. **Blank lines and separators**: the helpers that keep blank lines between blocks right, and who
   calls which.
5. **Keeping this map fresh**: the lint that checks every reference here, and how to add a row.

**How to read a row.** The entry is where you put the breakpoint. The rule is the thing that's
been broken before, and nearly every one is the same rule in a different costume, rule 4 of
[`rules.md`](rules.md): a behavior's logic lives at the one place every path crosses, not at the
call sites. So when you want to add a branch at one of these files, the rule in that row is what
you're arguing with.

A few of the words the repo coined survive in symbol names (`HeightOracle`,
`clampToLandableRaw`). Since this may be your first doc in the repo, keep
[`glossary.md`](glossary.md) open beside it; every one of them is a line there.

## Keyboard and chords

**`Mod` folds Ctrl and Cmd, unconditionally.** `src/lib/schema/keybindings.ts` :: `eventToChord`
turns a `KeyboardEvent` into a normalized chord, and `e.ctrlKey || e.metaKey` becomes the single
token `Mod`:

```ts
eventToChord(new KeyboardEvent('keydown', { key: 'b', ctrlKey: true })); // 'Mod+B'
eventToChord(new KeyboardEvent('keydown', { key: 'b', metaKey: true })); // 'Mod+B', the same string
eventToChord(new KeyboardEvent('keydown', { key: 'z', ctrlKey: true, shiftKey: true })); // 'Mod+Shift+Z'
eventToChord(new KeyboardEvent('keydown', { key: 'Shift', shiftKey: true })); // null: a held modifier isn't a chord yet
```

So nothing in the tree detects the platform (no `navigator.platform`, no `isMac`). The Playwright
harness does have to press a real OS key, so its helpers spell every editor chord `ControlOrMeta`
and let Playwright pick. A chord the editor doesn't claim (native word-jump, word-delete) stays a
literal `Control`, because macOS binds those to a different key. A branch that reads `ctrlKey`
alone and drops Cmd is invisible to e2e on a Linux runner, so its regression test belongs in the
unit suite, driven through a synthetic event like the ones above.

**Where a chord resolves.** `src/lib/schema/commands.ts` :: `resolveBinding` takes the chord, the
kind, the consumer's overrides and which plugins are on, and checks the consumer's overrides, then
the kind's own `keymap`, the editor-global keymap and the plugin-global keymap, in that order
(`docs/design/editor.md` § 5). It hands back the binding, or `null` when nobody claims the chord:

```ts
const all = everyInstalledPlugin; // src/lib/schema/plugin-activation.ts
resolveBinding('Mod+B', 'paragraph', undefined, all); // { chord: 'Mod+B', command: 'format.toggleStrong' } the kind's own keymap
resolveBinding('Mod+Z', 'fencedCode', undefined, all); // { chord: 'Mod+Z', command: 'history.undo' } the editor-global keymap
resolveBinding('Mod+Q', 'paragraph', undefined, all); // null
```

A chord bubbling up to a container (`resolveKindBinding`) stops before the global keymaps, so a
container never fires undo a second time for the leaf inside it.

**Where a new key goes.** A keystroke belongs in a keymap when it maps to a **command**: a named
id the focused block's `runCommand` or a global handler can run. Bare keys are fine there (Enter,
Tab, Backspace and Delete are ordinary keymap entries on prose kinds). A keystroke stays a
hand-written keydown branch only when a command can't carry it: the gesture needs an event a
keydown doesn't have (whole-block copy needs a `ClipboardEvent`), or it belongs to a passing state
rather than a kind (a selected inline widget, an open menu, the gap caret). If you're writing one
of those, your file claims a chord by hand, and it has to join the manifest.

**The manifest** is `src/lib/schema/reserved-chords.ts` :: `HARDCODED_CHORD_SITES`: one entry per
library file that reads a modifier flag, listing the chords it claims outside every keymap and the
key literals it compares. It's what keeps `reservedChords()` honest (the public set of chord
strings a host page reads to avoid colliding with the editor).

**And here's the one place the codebase's instinct is inverted.** A listed file keeps its literal
key comparisons. Pulling four `e.key === 'ArrowUp'` checks behind a shared `isVerticalArrow()`
helper is exactly what rule 4 asks for anywhere else, and here it fails
`src/lib/test/invariants/lint/reserved-chord-manifest.test.ts`, because that test checks each
entry's listed keys against the literals in its file. Take the literals away and the test has
nothing to check against. If you need the helper anyway, teach the scan about it first.

## The reveal path

A document is windowed, the block you must touch isn't mounted, and you need its DOM. Undo, a
search jump, a consumer's `setSelection` and a collapsing range all hit this. It gets its own
section because the chain runs through most of the rendering stack and no single file along it
names the whole path. What it does and why is `docs/design/virtual-rendering.md` § Doing something
to a block you can't see; this is where each step lives.

```mermaid
flowchart TD
    CALLER["a caller that must touch DOM"] --> PICK{"which primitive?"}
    PICK -->|"mount only (a history swap)"| MOUNT["reveal the path"]
    PICK -->|"mount + viewport (a navigation)"| SCROLL["hold the target, mount, scroll"]
    SCROLL --> MOUNT
    MOUNT --> LEVEL["descend one path level"]
    LEVEL --> HIDDEN{"into a collapsed body?"}
    HIDDEN -->|"yes, and it may open one"| OPEN["open it: one undo entry"]
    HIDDEN -->|"yes, and it may not"| GIVEUP
    OPEN --> SLOT
    HIDDEN -->|no| SLOT{"child's component ref set?"}
    SLOT -->|yes| NEXT["next level"]
    SLOT -->|no| WRITE["the list asks the scroll owner<br/>to scroll to the index's offset"]
    WRITE --> INWIN{"index still in window?"}
    INWIN -->|"provably not"| GIVEUP["give up now; the caller<br/>keeps the selection as paths (VR-5)"]
    INWIN -->|yes| PUB["the list re-slices, the host<br/>mounts and hands up its ref"]
    PUB -->|"one tick later"| NEXT
    NEXT --> LEVEL
    LEVEL -->|"path exhausted"| CARET["place the real caret"]
```

**The entries.** `src/lib/editor-rects.ts` :: `createEditorRects` is the navigation side
(`reveal`, `scrollTo`, `navigateTo`, which the outline and the search bar use): it mounts, scrolls
once, and holds the block where it landed while the heights around it catch up. Only a navigation
opens a collapsed body on the way. A caret goes through `src/lib/selection/caret-landing.ts` ::
`createCaretLanding` instead:

- `land` takes an edit's caret (and the inline menu's, the link card's);
- `navigate` takes `navigateTo`'s;
- `restore` takes a stored selection (undo and redo, `setSelection`, a mode switch, a range
  collapsed by an arrow, the find bar handing the caret back);
- `park` takes the moving end of a Shift+Arrow range, which mustn't end the range.

All four mount the same way, and the caret landing decides which path actually has to be on screen
(a table endpoint mounts its deep cell). A recorded gap caret goes back through
`src/lib/selection/selection-restore.ts` :: `restoreGapCaret`.

**Where a cell endpoint's caret goes is answered in one place.** An endpoint inside a table
addresses the table block by cell index, so every reveal and every caret placement asks
`src/lib/selection/selection-state.svelte.ts` :: `cellLandingFor` rather than resolving the deep
`[table, row, col]` path itself. A site that skips it places a cell index as a character offset
on the table, which lands somewhere random in the grid's text.

**The descent.** `src/lib/block-lists/child-list.ts` :: `descendTo` follows the path down through
each level's `ChildList` (the root, every container, the table and each row provide one). At each
level `src/lib/block-lists/child-refs.ts` :: `revealChildOrWait` moves on if the child is
already mounted, and otherwise asks the list (`src/lib/windowing/list-windowing.svelte.ts` ::
`createListWindowing`) to scroll to that index. `src/lib/components/BlockList.svelte` re-slices
and `src/lib/components/BlockHost.svelte` mounts and hands up its ref. Every `ChildList` has to
answer `isInWindow`, which is how the descent knows to give up instead of waiting forever.

**The scroll.** Scroll writes go through `src/lib/windowing/scroll-owner.ts` ::
`createScrollOwner`. The scrolling wrapper registers its target with the owner (`place`) before
its first await, so the pointerdown that started the jump can't release it. Nested containers get
their window from `src/lib/windowing/use-container-windowing.svelte.ts`; a table's cells never
window, so a far column is scrolled into the grid's own box instead.

## Blank lines and separators

A blank line between two blocks isn't a node. It's the next block's `leadingTrivia`, which means
a blank paragraph **is** the separating line of the block under it, and any operation that fills,
deletes or replaces a blank block has to restore a separator somebody else was relying on. Get it
wrong and the document saves fine but reloads as a different number of blocks. Read
`docs/design/syntax-tree.md` § Blank lines before touching any of this: two byte-equivalent
spellings exist, and which one you're holding decides which helper applies.

The helpers live at the head of `src/lib/tree-operations/settle.ts` (`clearRedundantSeparator`,
`dropDoubledSeparator`, `restoreSeparatorOnFill`, `restoreSeparatorAfterBlank`,
`settleSeparatorOnBlank`). Each takes a `BodyParent`
(`src/lib/tree-operations/node-primitives.ts` :: `BodyParent`), the children plus the container
that owns them, since that container's fence lines decide where a blank line may sit.

Almost nothing calls them by hand. A splice settles through one of two entries: `settleSeparator`,
which the commit runs over every scope's change, and `spliceChildrenSettled`, which the
path-addressed helpers in `src/lib/tree-operations/path-mutate.ts` and
`src/lib/tree-operations/cleanup.ts` splice through. The callers that still carry it by hand, each
saying why at the site:

- `insertParagraph` in `src/lib/editor-actions/block-edit-core.ts` (the gap caret, the trailing
  insert row, insert-below, a character typed on a block focused whole);
- the content entry's own branches in `updateNodeContent`;
- a range delete inside one block, in `src/lib/selection/range-delete.ts`;
- the reorder in `src/lib/tree-operations/reorder.ts` :: `reorderChildrenWithTrivia`, which moves
  blank lines by position and asks `settleSeparatorOnBlank` for each one it moved.

One helper sits outside them: `src/lib/tree-operations/list/sublist-separator.ts` ::
`settleSublistSeparator` gives a list right under a paragraph, whose first item's line is empty,
the blank line that keeps its marker from reading as a setext underline. The item moves, the
chain rebuild and the splice settle all ask it.

The document's last line, the one line allowed no line ending, has its own file,
`src/lib/tree-operations/open-tail.ts`. The commit calls `endWindowLines` before it repairs the
blank lines around the edit, and `keepOpenTail` once the containers rebuild. An edit never writes
that ending itself.

**When a join reads differently.** Some joins reload as fewer blocks than were there (a list newly
above indented code, a heading demoted into the paragraph under it, a paragraph put right above
its own `===` underline). The tree then converges to what a reload would read, and
`docs/design/editor.md` § 8 says why. `src/lib/tree-operations/settle.ts` :: `absorbSeamReading`
answers one join, and everything that disturbs one asks it: `splitNode` directly; `deleteNode`,
`updateNodeContent`, both splice entries and `reorderChildrenWithTrivia` through
`absorbWindowSeams`, which checks both edges of a splice. Since the block above may end up holding
the written text, the content entry reports where it went, and the caret follows
`src/lib/tree-operations/content-write.ts` :: `settledCaretPosition`. Before it asks, the content
entry closes any construct the write itself left open (`closeWrittenConstruct` in the same file),
so a half-typed construct doesn't swallow the lines below it.

The one join no scope can see is a container's own slot in its parent, since a change inside a
container changes what it interrupts. `src/lib/tree-operations/chain-rebuild.ts` ::
`rebuildUnsharedChain` asks it on the way out of the ancestor rebuild, and
`src/lib/editor-actions/ancestry-folds.ts` publishes the scope that collapse changed. A caller
that can't reconcile that splice passes `null` and declines; which caller takes which stance is
listed in `src/lib/test/invariants/lint/ancestry-fold-sink-thread.test.ts`.

## Keeping this map fresh

Write a reference as the full path from the repo root, plus a symbol only where the symbol is the
thing to find (`path :: Symbol`). No line numbers or signatures; they rot.

`scripts/check-codebase-map.mjs` runs inside `npm run lint`, and on its own as
`npm run docs:map:check`. It reads every backticked `src/`, `docs/` or `scripts/` span in this
file and every other `docs/design` and `docs/contributing` doc, and checks the path exists and,
for a `path :: Symbol` span, that the symbol appears in that file. A span that doesn't start with
one of those roots isn't checked at all, which is another reason to write the full path. It also
checks every `<doc>.md § Section name` pointer in the tree names a heading that doc still has.
When everything resolves it prints one line and exits 0:

```
$ npm run docs:map:check
codebase-map: … references resolve (… naming a symbol) across … files in docs/design, docs/contributing; … § pointers resolve across … files
```

Otherwise it lists each broken span and exits 1, so a deleted file or a renamed export goes red
on the commit that moves it. What it can't notice is a responsibility that moved while both names
survived, or a rule that stopped being true. That part is on you: **a moved entry point moves this
map in the same commit**.

Adding a row: name the behavior the way a user would say it, the file (or `path :: Symbol`) where
its logic lives, the rule that's been broken there, and the spec section that explains why. When
the map runs out, `docs/README.md` points you at the design doc for the subsystem.
