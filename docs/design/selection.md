# Selection, search, clipboard

How the editor selects things (inside one block, across blocks, a widget selected whole, the caret parked between two blocks, and the caret bar it draws for itself), plus find and replace, and copy, cut and paste. It's for whoever's about to change any of that, and it leans on the terms [`editor.md`](editor.md) sets up in its first three sections, so prob read those first.

1. Right below this list, with no heading of its own: selection inside one block, the clicks the editor takes over from the browser, a widget selected whole, and dragging a selection somewhere else.
2. [The drawn caret](#the-drawn-caret): the caret bar the editor paints itself, where it hands the job back to the browser, and what asks it to repaint.
3. [Cross-block selection](#cross-block-selection): a selection spanning several blocks, how you start one, how it's painted, and what each key does to it.
4. [The gap caret](#the-gap-caret): a caret parked between two blocks where neither one can hold it (a table right above a code block, say).
5. [Search](#search): find and replace, which reads the document and changes nothing until you replace something.
6. [Clipboard](#clipboard): copy, cut and paste, and the order a paste tries its options in ([The paste pipeline](#the-paste-pipeline)).

Single-block selection is the browser's: native selection inside the block's contenteditable, its caret (drawn by the editor on a fine pointer, at the browser's own position; see The drawn caret, below), native `::selection` paint, with only copy/cut intercepted. Except for the click sequence. From the second click of a run the editor takes the gesture over, because the browser's idea of a word depends on the platform (Windows grabs the space after it) and its word walk happily wanders into a rendered formula beside it. So: two clicks select the word, three select the block's content, and dragging from either grows the selection a word or a block at a time, across blocks too.

- The word comes from segmenting the text the word delete reads, the way the screen shows it: a hidden marker isn't in it, and a widget counts as one character of its own. So in live mode double-clicking the `b` of `a**b**c` gets you `abc`, and `_word_` gets you `word`. In source mode the underscores are on screen and `_` is a word character, so you get `_word_`, like a code editor would. The two share word boundaries, and the delete reaches a bit further (Ctrl+Backspace also takes any spaces between the caret and the word).
- There's no fourth level on purpose. Mod+A twice already selects the document, and a jittery triple-click that selects everything right before you type is a great way to lose a document.
- A double-click on an inline widget is still the widget's own business. The third click is the block's, unless the editor already holds that widget selected whole, which an image's own click handling does from the first click of the run.

A widget **selected whole** (an image after a click on it, or a live `<br>` an arrow key steps onto) is a selection the editor keeps for itself.

- While one is, no caret shows. The browser still holds one, collapsed at the widget's edge and hidden, because text that arrives with no key (a soft keyboard, dictation, an emoji picker, an IME) goes only to a selection; the editor puts it back there whenever the browser moves or drops it (`selection/widget-caret.ts :: writeWidgetCaret`). The widget owns everything that arrives: text replaces it, a delete removes it, and an IME composition started there removes it first, so the composed text takes its place and one undo puts the widget back (`selection/cross-block/range-replace.ts :: replaceWidget`). No read treats that caret as the user's: `getSelection()`, `selectionChange` and an undo entry answer the widget's edge its selection came from, and the block's own caret reads answer as with no selection. Under forced colors Chromium shows the caret anyway, since `caret-color` can't hide it there.
- The widget lives in the same selection state as a cross-block range and the gap caret (`selection/selection-state.svelte.ts`), and that state has one writer for all three, so any caret or range the editor puts down ends the widget on its way in. `selection/place-caret.ts :: selectWidgetWhole` is the one place a widget gets selected.
- A Shift+click grows a range from the selected widget instead of from that dropped caret, into another block too.
- It shows, so the key that replaces it never replaces something you couldn't see. The widget wears the same tint a text selection gets, painted by `selection/widget-selection-paint.ts`, the only thing that puts that tint on a widget. A line break has no box to tint, so it gets a narrow block at the end of the line it breaks, the way a word processor shows one. An image keeps just its editing ring wherever the ring shows, which is every mode but reading.

Dragging a selection and dropping it somewhere else is the editor's too. The browser's own drop is two edits, each committed on its own (and the insert lands at offset 0 once the delete re-rendered the block), so `selection/selection-drop.ts` cancels the native pair and moves the source surface's own bytes through the paste transforms as one undo entry. A shape it can't move yet (a drop onto a table cell, or onto a block with no character position) is cancelled outright rather than left to the browser, because the native drop loses bytes on undo. Cancelling takes the browser's drop caret away too, so while the drag is held the editor draws its own where a click would land, and draws none over a shape it will decline.

## The drawn caret

On a fine pointer the editor draws the caret itself: one bar per editor, sitting inside the block it draws for, while the browser's selection stays exactly where it was, so typing, IME and screen readers keep reading the real one. The same bar also draws where the browser can't, on any pointer: beside an inline widget, across a gap between blocks, and at a code chip's edge, whose outside stop has no caret position of its own. An attribute on that one editable (`data-caret-drawn`) hides the browser's caret there and nowhere else, so the find bar, the link card and any plugin's own field keep their native carets. Where it can't draw, it steps aside and the browser's caret shows, so there's always exactly one:

- a composition, or the shown source of a block that writes it on leaving (a math block);
- beside a text-height inline widget (an emoji, a formula) that no click put the caret beside (an arrow key got there, say), where the range has no box to draw at;
- anywhere the range's box isn't where the browser paints its caret: the spaces a line soft-wraps in, a caret a scroller inside the block has clipped out of view (a code block scrolled sideways; the bar comes back when it scrolls into view), and a code chip's edge where no look says which side of the border the next letter is on;
- forced colors, a touch screen, or a host that set the `caret` prop to `'native'`. Beside a widget, at a gap and at a chip's edge, only forced colors do.

At a code chip's edge the bar draws against the chip's own box, since there the range's box and the browser's caret disagree by a few pixels: in the chip's padding when the next letter types inside the chip, 2px past its border when it types outside (`caret/drawn-caret-measure.ts :: chipStopBox`, the `chip` state). Which side comes from the caret's look, so the bar always shows what the next letter does, wherever the browser left the caret.

A click beside an inline widget hands the drawn caret the edge it meant (`EditorServices.drawnCaret` :: `armWidgetEdge`), keyed by an object the block makes for itself. The editor holds one such edge, and a paint only reads it back through the focused block's own key. Typing, an arrow key or a click elsewhere lets it go.

Beside a picture the bar draws on every route, whatever put the caret there (a click, a key, a merge, an undo, the browser's own arrow), since the browser paints its caret there the whole line box tall. A picture is any widget whose kind declares `frame` (the built-in image does, and a plugin's tall widget can). The paint finds the picture beside the caret itself (`browser/caret-spot.ts :: frameBeside`) and stands the bar at its edge, at the height of the text on its line, which is where the next letter lands. A picture that ends its block has no text after it, so the render leaves a caret anchor there (a `<br>` holding no text, which every read skips) just to give that line a text-height box to measure. On Firefox an empty line's box is the whole line box, so there the bar is as tall as Firefox's bar in an empty paragraph.

Some clicks move the caret after the browser put it down on the pointer-down: beside a widget, in hidden marker text, or inside a container's marker prefix (a footnote definition's `[^label]: `, say). For those nothing draws, bar or browser caret, until the click lands, so no frame shows a caret where it won't stay. The drawn caret decides at its own pointer-down (`browser/offsets.ts :: clickMovesCaret`), so a click handler that starts moving the caret out of some new kind of spot adds that spot there.

Two things move the caret, and each gets painted its own way:

- **The editor writes it.** Every caret and range the editor puts down goes through the editor's one caret writer, `EditorServices.caretWriter` (`browser/caret-writer.ts :: createCaretWriter`), and each write asks for a paint. The paint runs once per task after `tick()`, past Svelte's flush and the block's height measure, so it reads a layout that's already clean and the bar lands in the same frame as the letter. If your code changes the caret's line after the paint without writing the caret, call `EditorServices.drawnCaret.request()` yourself. The dev check G1.76 catches a missing one only at a `selectionchange` that finds no paint pending, so don't count on it.
- **The browser moves it** (an arrow it handles, a click, a drag, IME). That arrives in a later task, so the paint for it runs at the next animation frame, armed by the key or pointer event. It's the one `requestAnimationFrame` that touches the caret, and it only reads and paints (`caret/drawn-caret.svelte.ts`).

The bar's shape shows the format the next typed letter will get: heavier for bold, slanted for italic, a tick for strikethrough. The shape comes from `components/blocks/text/next-byte.ts :: nextByte`, which asks the typing path itself where a letter would land and what it'd sit inside, so a change to how typing places bytes changes the shape with it. Any change to what the caret memory answers asks for a paint itself, which is how an arrow that only switches sides, or a format chord, reshapes a caret that didn't move. A new memory method that changes an answer calls `onChange`.

The bar is meant to look like the browser's caret. The paint puts its edges on whole device pixels, in the pixel column the letter boundary falls in (where Chromium puts its own caret, give or take a column: it floors in the editable's own pixels first), and colors it with the computed `color` of the element holding the caret (`caret/drawn-caret-target.ts`, `caret/drawn-caret.svelte.ts`). The stylesheet rounds every width to the nearest device pixel, as the browser does its caret's, so a new shape's lengths go in `editor.css`'s device-rounding block too (G4.166 fails one that doesn't).

## Cross-block selection

Two endpoints, anchor and focus, each a path plus an offset in that block. `selection/primitives.ts` :: `SelectionPoint` is the type, a union of two shapes told apart by `cellCoordinate`: a character offset into `raw`, or a row-major cell index inside a table. Code that reads an offset checks the flag, not the block's kind. `SelectionState` flags every endpoint on a table's path as it stores it, and a restore does the same to a snapshot's or a host's plain offset there. The one exception is a pair inside one cell (a finger's word there), which keeps the cell's own path and its text offsets, and only while both ends stay in that cell (G1.178).

Same path on both is a range inside one block, which the browser handles, except a finger's, which the editor takes over (On a touch screen, below); different paths mean the editor manages all selection rendering. The native caret and native `::selection` are suppressed (via `[data-painted-range]` on the editor root) exactly when the overlay paints instead, one predicate for both, so a stored pair the overlay declines to paint keeps its native caret rather than showing nothing at all. The state is lazy, its fields null in single-block mode, with a normalized `start`/`end` pair in document order derived from anchor/focus.

- **Entering it:** a mouse or pen drag that crosses out of the starting block (rAF-throttled, autoscrolling at viewport edges; a point off every block resolves to the nearest one, so a drag into the margin extends rather than stalls; the release resolves the drag at its own point before anything else on the page hears it, so a popover you show on release can't move where the drag ends); Shift+Arrow past a block edge; Shift+PageUp/PageDown from a caret; Mod+Shift+Home/End to a document boundary; Shift+click into another block; a second Mod+A (the first selects within the focused block, natively), or the first one where that would change nothing, since the block is empty or already all selected (and a block focused whole has no text to select first).
- **Moving its end:** Shift+Arrow, Shift+Home and End (Cmd+Shift+Left and Right on a Mac), Shift+PageUp and PageDown and the document edges move the focus through `selection/keyboard-extend.ts`, and the page follows the focus wherever it lands, even back inside the block the range started in. Inside one block, Shift plus a word key, Home or End lands where the editor decides (`caret/caret-motion.ts`), the same on every engine, and so does a Shift+Arrow across something the caret can't stop inside; any other Shift+Arrow is the browser's. The exception is a Mac's Cmd+Shift+Left or Right over a range, which the browser keeps: it grows the range at its start for Left and its end for Right, the way macOS does everywhere. A focus on a table cell steps a row at a time. A page key steps one screen of the editor at the column vertical keys keep (`selection/page-step.ts`): it finds the block a screen away in the height tables, so a block windowing hasn't drawn yet gets mounted first, and it starts from wherever the end is, even if you scrolled it away. A new key that moves an end writes it there too, since that's the bit that scrolls it on screen (G4.229 fails one that doesn't).
- **Rendering it:** every `BlockHost` mounts a `SelectionOverlay`, and so does a list item, which renders no host of its own yet holds children at ordinary block paths. Where the range starts and ends comes from `selection/range-coverage.ts` :: `rangeCoverage`, the answer the delete and the format toggle read too, and which blocks it boxes comes from the bytes a copy of it takes (see Clipboard below). Both are worked out once per selection change.
  - A block whose bytes all sit inside the range's, while its parent's don't, takes one full-block box, its own markers and frame included, and its descendants take none, so nothing paints twice. That's `selection/range-bytes.ts` :: `rangePaint`, and `selection/primitives.ts` :: `classifyBlockForSelection` asks it for every block. So a range from a quote's first letter boxes the paragraph and leaves the quote's bar bare, since the `> ` before that letter isn't copied either.
  - An endpoint block the range only partly covers measures partial rects and widens them to its line edges (`components/overlays/rects.ts` :: `reachLineEdges`): the start block runs from its point to its right edge and takes every line below whole, and the end block the mirror of that. A container holding an endpoint paints no box of its own, and a range inside one block (a finger's word, a rectangle of cells) paints its own rects without the widening. A cell has no host of its own, so a word in one is painted by its table's overlay, which finds the cell the way the decoration overlay does (`core/coordinate-spaces.ts` :: `gridCellOf`).
  - A block that scrolls internally (a wide table, a long-line code block) gets a passive scroll listener and a re-measure, so highlights track the content underneath.
- **One region:** a range across blocks reads as one selection, the shape a code editor paints. Every line between its first line and its last spans the block column, padding, margins and a container's rail included, and only the start line's text before its point and the end line's text after its point stay bare. `components/overlays/SelectionGapFill.svelte` fills whatever no block's own paint covers, and only while the range spans blocks.
- **On a touch screen** a finger's drag is the browser's: it scrolls, or a long press selects a word. So a finger's drag on the text never opens a range, and a press that turns into a scroll leaves a range or a selected picture alone. A tap clears them. A long press or a double tap ends any range too, and once that press is over the editor takes the word the browser picked as its own range: it paints it, draws its two handles and collapses the native selection to a caret, so no phone draws its own handles or menu on it (`selection/finger-takeover.ts`). `selection/pointer-gesture.ts` is still the one place that asks whether a press is a finger (G4.279).
  - A block with no positions inside (a table of contents, an equation) joins a drag once the pointer crosses its centre line from the anchor's side, so a sweep that only touches its edge doesn't take it. A finger's handle takes it a line past its edge instead when that's nearer, since on a phone a table of contents can be most of the screen and the finger covers what's under it (`selection/drag-pointer.ts` :: `reachesWholeBlock`, for the cell drag too).
  - The press is over at its `pointerup`, or at the `pointercancel` Android (and now and then iOS) ends a long press with. Safari writes its word back a few milliseconds after the lift, and Android's held finger keeps growing the range, so until the next press the editor takes any range the browser writes in that block the same way (G1.169). No timer decides any of it.
  - The editor owns a range inside one block only when a finger made it (G1.170). A mouse's or a keyboard's stays the browser's, so a hardware keyboard's Shift+Arrow, or a mouse's Shift+click in the same block, hands a finger's word back to the browser. Who holds a range and whether it sits inside one block are two questions with two names, `SelectionState.ownsRange` and `rangeInOneBlock`: a link, a heading level, Mod+1 and the first Mod+A ask the second, so they work on a finger's word as on the browser's. A table cell counts as a block here: its word is the editor's range at the cell's path, its end handle grows it into a rectangle of cells, and an edit over it goes through the cell's own write, since bytes written at a cell's slot read back as a cell (`tree-operations/list/task-paragraph.ts` :: `slotReaderAt`). A long press there opens no cell menu; a finger gets a button at the focused cell instead (`components/blocks/table/TableBlock.svelte`), its one way to the row and column actions.
- **Selection handles:** the editor draws a handle at each end of every range it paints: across blocks, a rectangle of cells, a block held whole, or a finger's word (`components/overlays/selection-handles.ts`). With the native selection a caret, they're the only handles on screen. A handle starts the drag a mouse press would (`selection/drag-pointer.ts`, or the cell drag in a table), and one dragged back into the range's first block keeps the range the editor's. For the drag's length the handles, the toolbar and a table's cell menu button take no hit test, so the point under the finger names the text rather than the chrome over it.
- **One menu:** a finger's range has no keyboard chord and no phone menu, so the selection toolbar is its menu, with Cut and Paste beside its Copy, sitting above the range clear of the handles. With `selectionToolbar` off it keeps that clipboard row alone. Android's long press hands the page a `contextmenu`, which the editor cancels and answers with nothing. A menu's Cut and Copy run the browser's own command first, whose event the editor's copy step answers as it answers Ctrl+C, so a frame with no clipboard permission still copies. Only when no copy step took it (WebKit fires nothing over the lone caret under a range the editor holds) does the menu write the range itself (`components/menu/clipboard-actions.ts`), and a Cut removes its text only once that write lands. On iOS the toolbar's Paste reads the clipboard, so text copied in another app goes through Safari's one-tap Paste prompt.
- **Considered and not taken,** both measured on the phones:
  - _Keep Safari's range and hide its handles._ A transparent `caret-color`, set before the range forms, hides Safari's handles (and its highlight), and the editor's handles still get the finger. But Safari's menu comes with its range and can't be hidden while the range stands, so it would show beside the toolbar, and the two phones would run two selection models.
  - _One editing host over every block,_ what Gutenberg does for iOS. Both browsers' handles then cross blocks natively and survive a far block unmounting mid-drag, and Gboard composes in the host. It gives up the per-block editing host this design rests on: every key, input and clipboard handler would find its block from the selection, typing costs more as the host grows (Gutenberg measured about 40% more per keystroke at 1,400 blocks), a screen reader hears one big textbox, and BlockSuite turned its host off on Android after IMEs composed into it without committing.
- **Exiting it:** a click or an unshifted arrow collapses back to native single-block selection.
- **Replacing it:** anything destructive over the range (Backspace, Delete, cut, typing, an IME composition, paste, and a command key, below) goes through one replace, `selection/cross-block/range-replace.ts` :: `replaceRange`. It removes what the range covers, through the range-edit core's bytes for that range (`structural-edits.md` § Structural operations has the rules), then does the key's usual thing at the caret that's left, all as one undo entry, and the replace itself lands one caret. Text typed or pasted over a range across blocks, or over a block with no text held whole, is one step instead: the core answers it whole in one commit, a typed key with the bytes a one-line paste of it would leave (`range-edit/edit-range.ts` :: `editRange`, the `{ text }` gesture, and [The paste pipeline](#the-paste-pipeline)). A key that types a character comes to the replace at its keydown, before any block's own key handling sees it, since beside a picture with no text next to the caret no engine sends a `beforeinput`. `schema/keybindings.ts` :: `typesCharacter` says which keys type, for the range and the blocks alike. What goes depends on two things, the kind of gesture and what the range covers, and the replace keeps that as one table in the same file:
  - Backspace, Delete, cut and the command keys take a whole table, row or column inside one table out, however deeply the table's nested, so a command key ends exactly as Backspace and then the key would.
  - Typing or pasting over a row, a column or a smaller rectangle of cells clears them and puts the text in the first one instead, since a removed row leaves nowhere to type.
  - Typing or pasting one line over a range inside one cell (a finger's word there) is one write of the cell (`range-edit/edit-range.ts` :: `textInCell`). A cell can't store a space at its edge, so removing first would eat the space the removal leaves next to the text, and `x` typed over `apple` in `apple pie` would come out as `xpie`.
  - A range holding one block whole (a table with every cell selected, say) has no survivor to act at. Typing and paste replace the block in its own slot, while the other keys take it out. Focus parks on the editor root, whose keydown and clipboard handlers are that range's only entry.
  - An IME composition removes the range before the IME writes anything (a table keeps its cells, emptied), and its caret waits where a typed key's text would go: before the rest of a block's text the range ended partway through, on a line it emptied, else in an empty paragraph opened where the range was, the one the caret between blocks opens (`range-edit/edit-range.ts` :: `placeAnswer`). So the composed text never joins a block the range didn't reach. It goes in through typing's own write, which keeps a blank line under a container's opening row where a typed key's text doesn't. The IME keeps composing wherever the caret is, so the composition carries on in the block the removal kept, even when the block it started in is gone (Ctrl+A twice leaves the browser's caret in the last block, say). That block opens the composition at its first composed character, and the composed text joins the removal's undo entry.
  - When the range took the block it started in (a table held whole, say), the caret the delete leaves sits in the block beside it. If that caret is on the block's syntax rather than its text (a code fence, a heading's `#`, a rule), typing, pasting or composing there would turn the block into something else. So the text goes in a paragraph of its own where the range was (before a block below, after a block above): the core names that place for typed and pasted text (`range-edit/edit-range.ts` :: `textPlace`), and the replace opens it for a table's cells (`selection/cross-block/range-removal.ts` :: `emptiedPlace`). Text over a finger's range inside one block is the core's answer too, which is the block's own write there, so it leaves what typing over the browser's range leaves. Where the removal's caret is a boundary between blocks, the paragraph opens at that boundary, the one a plain delete holds the gap caret at ([The gap caret](#the-gap-caret)), so a key and then a letter leave the blocks the letter typed over the range leaves. A caret on text the range left of its own (the rest of the block it ended in, a code line's too, or a line it emptied) takes the text where it is. A caret on a block the range never reached takes no typed, composed or pasted text: the paragraph opens where the range was. A caret where the text below the range joined a block above takes it too, since no boundary is left where the range began. If the replace's paragraph can't open, the text is dropped with a dev warning, never written into the syntax.
- **Command keys over it:** a command key is whatever the keymap binds to a command that runs at a caret after the removal: a split, a hard break, a code newline, a cell's Enter (`schema/commands.ts` :: `AFTER_RANGE_REMOVAL_COMMAND_IDS`), or a plugin command registered with `overRange: 'afterRemoval'`. By default that's Enter and Shift+Enter, following the `keybindings` prop. A line break (Enter, Shift+Enter, a soft keyboard's) goes where text over the range would: before the rest of the text the range ended partway through, else on a line it emptied, else in an empty paragraph opened where the range was. Enter's break there is that paragraph, and Shift+Enter then breaks that empty line as on any other. So no break writes in a block the range never reached, and a plugin's command key goes to the same place. The keymap of the block at that place is the one that claims the key (`selection/cross-block/keydown.ts` reads the core's place), and that block runs its own command there: the place's commit and the command are two commits in one undo step. A title row's Enter goes on into the body, and its Shift+Enter breaks nothing. A break that arrives as input counts as one even where that block binds its key to nothing. A table's cells have no such place, so a key over them runs in the cell the removal leaves (`selection/cross-block/range-removal.ts` :: `cellLandingKind`). A bound key is never typed over the range, even one that also types a character (Ctrl+Alt is AltGr on Windows): if the block's keymap binds it to something else, or a container around the block the key lands in binds it, it goes on to the block and its containers, as it would from a caret. Where the place is a gap ([The gap caret](#the-gap-caret)) there is no block for the command to run in, so it runs in an empty paragraph opened there, which is Enter's own break.
- **Indenting it:** Tab, Shift+Tab and any other key bound to an indent command go to `selection/cross-block/range-indent.ts` :: `indentRange`, which asks each covered block what the key means for its own kind and does what that kind registered in `schema/range-indent-forms.ts` (a plugin kind registers with `registerRangeIndent`).
  - A list item nests or lifts exactly the way a caret's own Tab moves it, through `tree-operations/list/item-moves.ts`, and an item that can't move stays put while the rest still move. A code block shifts the lines the range covers. Prose and tables stay as they are.
  - Tab and Shift+Tab are taken over a range even when nothing indents, so focus never wanders off to the next control on the page. The range stays over the same text afterwards, and each press is one undo entry.
  - A selection inside one block asks its block the same question (`bindsIndentAt`), so prose takes the key and changes nothing rather than getting a tab typed over the selected text.
- **Re-kinding it:** a heading key (Mod+digit by default) or the toolbar's heading picker deletes nothing either. Every text block the range reaches takes the level the key sets inside one block (`tree-operations/heading-level.ts` :: `headingWrite`, a set, never a toggle), through the format toggles' one write (`selection/cross-block/format-toggle.ts` :: `headingOverRange`). A block with no text, a table cell and a to-do's text keep their bytes, a kind that binds the key to nothing keeps its kind, and the range stays over the same text, one undo entry.
- **Restoring it:** one route (`selection/caret-landing.ts` :: `restore`) serves the undo swap (a gap caret it recorded included), the consumer's `setSelection`, a mode switch, an arrow that collapses the range, a Shift+Arrow that folds it back into one block, and the find bar or link card handing back the caret it borrowed.
  - It resolves and clamps both endpoints, mounts what the caret will park at, then writes the state and places the caret inside one change-notification batch, so no notification reports a selection the restore is about to move (`commit-and-undo.md` § The event channel).
  - The caret goes where one can sit: a point on a list's own path goes into its first item, a point in a closed `<details>` body onto its title row (nothing opens), and a pair spanning a block with no text (a rule) comes back held whole, focus on the editor root.
  - Then, unless it's a mode switch (which keeps its own scroll), a caret off screen comes in to the nearest edge.

Across containers, "start wins": the text a removal joins takes the start's block and its write rules, and a container the range starts in stays, emptied if the range took everything it held.

**`measurePartialRects`: offset semantics by surface.** The hook's `(startOffset, endOffset)` shape is stable, but what an offset _means_ depends on the surface, and a new endpoint-capable kind picks one:

- **Text contenteditable** (paragraph, heading, code). Offset is a character index into `textContent`; a shared helper walks the DOM for wrapping-aware rects, so every contenteditable block reuses it with no per-block work; `SELECTION_END` clamps to the end of `textContent`.
- **Cell-based** (tables, any 2D grid). Offset is a cell index in row-major order, one rect per cell in `[start, end)`; the surface maps click/drag positions to cell indices on entry; `SELECTION_END` means "through the last cell".
- **Opaque single-unit** (thematic break, an embedded diagram). No interior positions: the valid offsets are 0 and the end of its own markdown, an endpoint landing inside snaps to whichever its side of the range needs (so copy and delete move the unit whole), and any non-empty range returns the bounding rect as a single element. A kind that needs finer granularity is the wrong kind.

A block that doesn't implement the hook still gets its box when the range covers it whole, but as an endpoint the range only partly covers, it paints nothing.

## The gap caret

One of the three selections the editor owns (the others are a cross-block range and a widget selected whole), and the only caret among them: a caret parked between two sibling blocks, at a boundary no block's own editing surface can reach. Between a table and a code fence, say, or above a document that opens with a table; without it those boundaries have no insertion point at all. A gap position is `{ parentPath, index }`: the boundary before child `index` of the container at `parentPath`, with the root as the empty path and `index === children.length` as the scope's trailing edge.

````ts
const doc = parse('| a |\n| - |\n\n```\nx\n```\n\nplain\n');
gapEligibleAt(doc, [], 0); // true: above a table that opens the document
gapEligibleAt(doc, [], 1); // true: between the table and the fence
gapEligibleAt(doc, [], 2); // false: a paragraph can host the caret itself
````

It's collapsed by construction and never half of a range.

**Eligibility is declared, never inferred.** Every kind declares `gapEdges` (`before`, `after`, `both`, or `none`) in its descriptor, and a boundary opens only when both blocks facing it declare the edge they present to it. `none` is the written-down no, required so that leaving the field out can't pass for a decision, and no selection or orchestration code names a kind. Among the shipped kinds:

- table, fenced code, and the bundled math block and math fence declare both edges;
- the thematic break and the mermaid diagram declare before only, since their focused Enter already grows a sibling below;
- the opaque containers (the callout kinds, details, the generic directive container) declare both edges, because their fences leave no textual escape hatch and two adjacent callouts would otherwise have no insertion point between them;
- strip containers (blockquote, list, GitHub alert) declare `none`, their unwrap and exit gestures already owning insertion at their boundaries.

The root's trailing boundary is excluded, since the move-past-end append already owns it; and reading mode, having no caret at all, has no arrival.

**A removal may hold a gap no arrow stops at.** When a range is removed (Backspace, Delete, a cut), the range-edit core names where the caret goes, and so it does for a Backspace or Delete that joins nothing (a paragraph's start under a row that is all name, beside a table of contents). If that place is a boundary between blocks, the caret is held as the gap there, whatever `gapEdges` says: under a fence that ends the document, under a title row left alone in its directive, between a paragraph and a fence where a rule was cut. The caret would otherwise sit on a block's syntax, and the next letter would break it. Three boundaries send the caret to the text at its byte instead. Beside a paragraph's own text in the same container, a letter typed there joins the paragraph anyway (except at the document's end, where the emptied line is a place of its own). At a quote's end, a paragraph below the quote doesn't count: the letter would stand inside the quote. A heading's text holds one line, so it doesn't count, and a letter typed under a heading opens its own paragraph. A boundary a closed container hides takes no caret, and neither does one among a list's items, where no paragraph can stand. `selection/range-bytes.ts` :: `heldGapOf` answers for the caret after the key, and for a letter typed over the range where it holds a gap. Before prose the range never reached, a cut keeps the text start, while text typed over the range opens its own paragraph. A Backspace or Delete that joins nothing holds the gap even beside the paragraph it was pressed in (`keyGapOf`), since giving way to that text would leave the key doing nothing; behind a closed container it lands on the container as any arrival does. A gap held this way is marked `held`, which lets it draw where the arrows' rule opens no gap; undo and redo carry the mark.

**Arrival** rides paths that already existed: a directional focus move stops at an eligible boundary instead of entering its target (covering the arrows and the Backspace/Delete-at-edge focus fallbacks together); a dead-space click whose y falls between two root bands lands there; the undo restore route parks one it recorded; a removal's landing holds one (above). A targeted landing (a numeric offset, a consumer's `setSelection`) never stops. Placing the gap ends whatever else the editor had selected, and any other caret the editor puts down ends the gap, through the selection state's one writer (above). A structural commit ends it as well, since the gap names a boundary index and an edit ahead of it moves what that index names.

**At the gap**, a printable key or an IME commit inserts a paragraph carrying the text, and Enter inserts an empty one; both go through the ordinary commit steps, so each is one undo entry and one `insertBlock` edit event. If the browser dropped a composition there (no `compositionend`), the next key ends it: the composed text becomes that paragraph and the caret goes into it, a typed letter joins the text, Enter opens an empty paragraph after it, and any other plain key does nothing else. Arrows, Backspace and Delete leave for the neighbour in their direction, and Escape leaves for the block above (the one below, at the first boundary of its list). With nothing below (a held gap at the document's end, or a gap ending its last container), ArrowDown and ArrowRight append a paragraph as they do from the last block, and Delete stays put, since it writes nothing. Shift+Arrow is deliberately the plain arrow: a single block selected whole isn't a representable cross-block state, and the per-kind shapes it would need are exactly the kind dispatch selection code refuses. A paste puts the clipboard's Markdown at the gap as blocks, through the same paste route `insertMarkdown` takes, so it's one undo entry and the caret lands at the end of what it pasted. Every other input is declined rather than guessed at. Focus lives on a hidden proxy (the drawn caret lays its bar across the boundary), which is what lets the editor-global chords resolve there as they do anywhere else. The proxy's focus never scrolls; the arrow move or the undo that put the gap there calls `src/lib/selection/caret-landing.ts` :: `showGap`, which scrolls just far enough to show it, so a new route that places a gap off screen calls it too.

**Undo stores it as itself.** An entry's recorded selection is either an editor selection or a gap position, so undoing the insertion returns the caret to the boundary the paragraph came from, and a restore whose container path no longer resolves degrades to the ordinary fallback landing rather than parking where nothing would paint it. **It isn't public.** The gap stays outside the `SelectionPoint` union, a freeze decision [`plugin-contract.md`](plugin-contract.md) § Payloads bound as-is records.

## Search

Find/replace is a **read-only view over the tree**: it renders nothing itself and mutates nothing until you ask it to.

- **Scan** (`search/`) walks the document by path, matching each _editable leaf's_ `raw`. Containers are skipped, not because they lack text but because their `raw` duplicates their children's (`structural-edits.md` § The container `raw` contract); the one exception, a childless opaque container, has no children to duplicate and scans its own `raw` as a leaf. Literal, whole-word, case-sensitive, and regex modes compile to one matcher interface, and an invalid pattern surfaces as an error string, never a throw.
- **Paint.** Matches are published as mark decorations (source `editor:search`) and the shared decoration overlay paints them; search was the engine's first client. The scan is memoized on the engine's edit epoch plus query and options, so an edit re-scans while navigation only remaps the active highlight. Decorations are bucketed by owning path once per run, so an overlay reads only its own bucket, and windowing follows for free: an unmounted block simply doesn't paint.
- **Navigate.** The active match is revealed through the same reveal primitive focus uses ([`virtual-rendering.md`](virtual-rendering.md) § Doing something to a block you can't see), so a match thousands of blocks away mounts, scrolls in, and highlights.
- **Replace** reparses only the affected _top-level_ subtrees and commits once per subtree, O(affected subtrees) rather than O(document), with one edit event for the batch (`commit-and-undo.md` § The event channel). Replace-all lands under a single undo entry, and a replacement into a table cell escapes the delimiters the cell's `raw` reserves, so it can't split the row.
- **Cost when idle: zero.** The decoration source lives only while the bar is open (opening registers it, closing disposes it), and the post-commit re-run is deferred off the commit path, never a synchronous per-keystroke scan.

The bar is on by default and switchable off (`searchBar` prop), bound to Mod+F / Mod+H; a consumer can drive the same controller headlessly through `getSearch()` on the editor instance.

## Clipboard

Clipboard text is always plain Markdown, and every copy, cut and paste is intercepted wherever it fires. Two extras ride along. A rectangle of table cells also goes on as an HTML table, because that's what spreadsheets read. And a copied range brings the editor's own entry, as `application/x-aragonite-range` and as an in-memory copy matched by its text, since Firefox hands a paste the text alone. A paste reads it back ([The paste pipeline](#the-paste-pipeline)). All of it is written in one place, `browser/clipboard.ts` :: `writeClipboardEvent` (G4.314); a menu's Copy goes through the async clipboard, which refuses a type of the editor's own, so its entry stays in memory.

- **Copy.** A copy is the range-edit core's copy of the range's bytes, inside one block and across blocks alike (`selection/range-clipboard.ts` :: `rangeClipboard`). The bytes are `selection/range-bytes.ts` :: `rangeBytes`: each end's byte in the document, widened over every block the range holds whole (see Cut). A heading held from its first byte to its text's end counts, so its underline or closing run is copied too. And the document's first caret position to its last widens to its first byte, so select-all over a document that's one quote copies the quote, markers and all (G4.315 keeps that reading in one file). In live mode a range over a `:::` row's whole text copies the title alone, the part a delete there takes (`live-mode.md` § 4.5). The editor hands the copy its cached source and a layout it makes once per content version, so a copy costs the range, not the document.
  - In live mode a format run the range cuts through comes along closed at each end, the way a cut there would take it, so a paste gives back what was cut.
  - A container the range enters or leaves comes along: its markers on every line the copy holds, and a fenced one's opening or closing line. So a range from a paragraph into a nested quote copies `> > As you` and not `As you` (G1.171). The container both ends sit in adds none, since a paste back lands inside it anyway: copy a word inside a quote and you get the word.
  - Other structure outside the range comes along where the copy would read as something else without it. A copy starting in a table's rows brings the header and delimiter rows, so it pastes as a table. One starting on a callout's or a details block's title row brings the container's opening with the part of the title it covers, and one ending inside an open details' summary closes the summary. In source mode a code fence the range runs into gets its closing line, unless the copy ends inside the opening line, so a paste never opens a fence that swallows what follows it.
  - A copy ending at a block's last letter brings no line ending. A closed details the range takes whole is copied whole, hidden body and all.
  - A rectangle of table cells copies as a GFM sub-table plus the HTML table, the same bytes whether the copy fires in a cell or at the editor root. It never reaches the core.
  - The selection survives the copy.
- **Cut.** A cut is its copy and then a delete, wherever it fires. The copy writes the clipboard during the cut event, before anything waits, since a menu's Cut is a scripted cut and the browser closes its clipboard data the moment the event's handlers return. Then a shown source hides, and the delete removes the range the copy read (`components/blocks/editable/clipboard-step.ts :: runClipboardCut` runs both halves for every kind of selection). Across blocks the delete is Backspace's bytes. Both halves come from the range-edit core's one answer for the range, so the clipboard holds what the delete took, save the blank line a block taken whole takes along with it (G1.199 runs every removal route against that answer).
  - The shared answer is `selection/range-coverage.ts :: coverRange` and then `rangeCoverage`. The first snaps table endpoints to whole rows, and takes a closed details whole when the range starts on its summary or ends past the summary's first byte, since its hidden body can't be half selected. The second says which blocks the range holds whole.
  - An endpoint on a block with no text position (a rule, or a table the range enters at its first row or leaves at its last) holds that block whole, unless it sits on the block's outer edge (a range that ends right where a rule starts never reaches it). An endpoint in text always keeps its block, even emptied.
  - The delete then truncates the endpoints it keeps at their offsets, removes what's held whole, merges what's left of the two endpoints into one re-parsed block (a table or a details title row never merges), and removes every container it emptied. A block the range only touches, ending at its first byte or starting past its last, merges when it holds text (a paragraph, a heading, which brings its text and leaves its `#` behind) or where Backspace would merge it, and otherwise stays whole as its own block, so a rule or a code block never turns into text. A range that ends where such a block starts still takes every block it holds whole before it: a closed details goes with its hidden body, a `:::` container with its closing line (G1.212). It's one undo entry, and the cross-block state collapses.
- **Focused block or selected widget.** A whole-block-focus block that holds focus, or a selected inline widget, copies or cuts its own Markdown on Mod+C / Mod+X: the range-edit core's copy of the block taken whole (its `raw` less the line ending that closes it, with the editor's own entry in memory), or the widget's source slice. These route outside the keymap because a keydown carries no clipboard event. A paste there lands after the block, as blocks, the way a paste at the gap caret does.
- **The menus.** The right-click menu and the table's cell menu ask `selection/held-selection.ts` whether there's anything to cut or copy, never the browser alone, since under a range or a widget the editor holds the browser's selection is just a caret (G4.296). A right press on the range as it's painted keeps it for the menu. One anywhere else ends it the way a click would, as long as a menu opens for what it pressed. A right-click in the margin or on one of the editor's own menus opens none, so the range stays. That's decided at the press, because Linux sends `contextmenu` on the press and Windows on the release. A menu's Paste over a range holding one block whole goes to the range, since focus is parked on the root there.
- **Paste.** Every paste arrives at one entry at the editor root (`components/editor-root/paste.ts`), whatever brought it: the event, a menu's Paste, `insertMarkdown`. The entry reads the clipboard once (`browser/clipboard.ts`), finds the place (the range the editor holds, the gap caret, the focused block's answer, or under a block focused whole) and hands both to the range-edit core. A block only says which of its bytes the paste replaces (`BlockComponent.preparePaste`), read the moment the event arrives, before a shown source hides. The paste is one undo entry, the caret lands after what was pasted, and undo puts it back where the paste began. A text field inside the root (the link editor, the language picker, search) and a plugin's own editable element keep the browser's paste.

### The paste pipeline

A paste is one step, `selection/cross-block/range-paste.ts` :: `pasteThroughCore`, at every place. Over a range across blocks it lands where text typed over the range goes ([Cross-block selection](#cross-block-selection)). In the step, the clipboard and the place go to the range-edit core (`range-edit/edit-range.ts` :: `editRange`), which answers with the document's new bytes and the caret. What joins the text at the caret, what lands as blocks and where blank lines go are the range-edit laws (`src/lib/test/range-edit/laws.ts`).

- **Two ways to commit.** A hidden edge, a pending mark and a pending break treat pasted text as they treat a typed letter: their records are spent where the core writes the text, before anything commits. Text that lands inside one top-level block then commits as that block's own write, the one a typed letter ends in, for its cost, where that write leaves the core's bytes and caret. Anything else is one byte splice (`commit-and-undo.md` § The byte splice), since a container rebuilds its own bytes around a block's write. Either way the edit event is `paste`, and its `count` is the number of blocks the paste landed as (0 for text).
- **The place decides text or blocks.** A caret in a block's text takes text. A gap caret, a block focused whole and, in live mode, a caret on a block's hidden syntax take blocks, a blank line apart from each neighbour.
- **What the paste joins keeps its own spelling.** Pasted items that join a list take its glyph, since `*` against `-` is no other kind of list (ordered against bullet is). A `:::` container whose body takes a closing line grows its fence, as its kind writes it (`range-edit/paste.ts` :: `landedAt`).
- **A clipboard's last line ending.** In a list item, and on the empty line an ending opened, an ending is Enter. Mid-text outside a list it is not: the first ending is the clipboard's own line break (`al‸pha` + `xy⏎` is `alxy`, then `pha` on the next line of the same paragraph) and the second is a blank line. In a list (the caret's, one the paste joined, or one nested in the caret's item) the ending opens the next item, empty, with the caret in it; under any block that left the list (a list of another kind, a rule the item gave way to, a quote) the item it opens heads the list's items below (`range-edit/paste.ts` :: `entered`). The ending also makes one line a block: `# h` with its line ending, pasted after text, lands as a heading, where `# h` alone goes in as text. The ending never leaves a blank line inside a list, and the caret lands where Enter's does, so the next letter types plain. Each later ending is another Enter where the one before left the caret: on the empty item the first opened, the second leaves the list or lifts a nested item (`RangeHost.enterOut`); on an empty line where Enter would only add another, it adds nothing. Line endings pasted alone are Enters from the first, and over a heading's whole text the heading gives way to its empty line. A trailing line of only spaces or tabs is a line ending; its spaces aren't written. A link definition holds no pasted line: lines pasted anywhere in one land as blocks under it.
- **The editor's own entry.** A copy or a cut writes one beside its text. A paste that still finds it, at the place the cut left the caret, puts the cut's bytes back exactly. Paste as plain text and Ctrl+Shift+V ignore it, and escape the text wherever it lands as Markdown.
- **Paste transforms** run where the clipboard lands as blocks, and never on the editor's own entry. Text that goes in as text (one line after text, a cell, a title row, a code body, plain text) isn't rewritten.
- **A table cell answers first** (`components/blocks/table/table-cell-paste.ts`, a row of the paste-surface registry). A grid (spreadsheet tabs or a GFM table) fills cells from the caret's cell or the selected rectangle. A clipboard of blocks slices the table at the cell's row and lands between the halves. Any other paste is text on the cell's one line.
- **Images** go to the host's `onPasteImage` first. The Markdown it answers is pasted where the paste was aimed, or over a range selected while the import ran.
- **A shown source that commits on blur** (a math block's) is its block's draft. Its paste is a splice of the shown text, and reaches the document when the source hides.

Don't build a `ClipboardEvent` to fake a paste: Firefox empties its `clipboardData` (G4.221). Read the clipboard with `browser/clipboard.ts` :: `readClipboard` and hand the read to the entry.

A cell's own answer and the range gestures commit through a `PasteCommitCoordinator` interface that an editor-actions factory satisfies, which keeps `tree-operations/` from importing back into `editor-actions/`.
